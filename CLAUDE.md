## The shape of the project

The frontend is shared and the backends are interchangeable. This is the whole architectural idea,
and the folder layout exists to make it true:

```
source -> lexer -> tokens -> parser -> AST -+-> interpreter   tree-walking (ladder #4)
                                            +-> compiler      AST to bytecode, runs on the VM (#5)
                                            +-> codegen       AST to native assembly (later)
```

```
MiaKomp/
  CMakeLists.txt
  src/          the language: token.h, lexer.*, ast.h, parser.*, interp.*, vm.*, compiler.*, main.cpp
  examples/     sample programs written in MiaKomp
  reference/    vm_original.cpp - the finished Exercise 3 VM, kept for reference, not built
  build/        generated by CMake. Regenerable, never edited by hand, never synced
```

`ast.h` is header-only: it is nothing but type definitions.

## Build

CMake, because this folder is expected to build on both the Windows machine and the Mac and a
hand-written per-platform task would have to be maintained twice. CMake generates the platform's
real build system from one description.

```
cmake -S . -B build          configure: read CMakeLists.txt, generate a build system into build/
cmake --build build          build: run that generated build system
```

On Windows the default generator is the Visual Studio one, which is multi-config, so a specific
configuration is selected at build time (`--config Debug`). On the Mac it is single-config and the
configuration is chosen at configure time instead. That asymmetry is normal and is the one place
the two machines visibly differ.

Warnings are set per target inside `CMakeLists.txt` (`/W4` on MSVC, `-Wall -Wextra -pedantic`
elsewhere) rather than in an editor task. The Exercise 3 log records what happens when the warning
level silently is not what it is believed to be: read the 2026-09-22 entry in the other CLAUDE.md
before assuming a build is clean.

## What I already know in C++

### Basics & build
- `#include`, `int main()`, `std::cout`/`std::endl`, compiling with `cl` (Windows) or `g++` (Mac)
- Commenting with `//`; debugging a compile error from the exact line/column the compiler reports
- **Turn warnings on**: `g++ -Wall` / `cl /W4` — they caught three real bugs in one session
  (parenthesization, out-of-bounds string-literal arithmetic, tautological comparisons)
- Editor tooling for brace/scope bugs: `Shift+Alt+F` re-indents to the *actual* brace structure;
  `Ctrl+Shift+\` jumps to the matching brace. Balanced braces in the wrong *place* still compile
- VSCode C/C++ IntelliSense setup (`.vscode/c_cpp_properties.json`, `includePath`) and a VS Code
  build task that compiles + runs the active file in one step

### Memory, pointers, references
- Stack variables, `&` (address-of), pointer declaration (`int*`), dereferencing (`*p`)
- Heap allocation: `new`, `delete`, `nullptr`, and that heap memory doesn't free itself
- Pointer to pointer (`int**`), multi-level dereferencing (`**pp`)
- **References** (`Board&`): an alias for an existing object — no copy, mutations visible to the
  caller, never null, never re-pointable. Like an auto-dereferenced pointer (`r.get()` not `p->get()`)
- `const T&` — the default way to pass a read-only object: no copy, no accidental modification
- Passing a **container** by value is a deep copy of everything inside it. C++ copies by default
  and never warns — the opposite of the Python instinct. Reflex: **if a function must change
  something the caller can see, or the thing is bigger than a machine word, it takes a `&`.**
  A recursive accumulator (counter, visited-set, table) is always a reference or it silently does nothing
- **Non-copyable types**: `std::random_device` (and mutexes, file handles, `unique_ptr`, sockets)
  delete their copy constructor — passing them by value is a *hard compile error*
- Uninitialized locals hold stack garbage and the compiler won't stop you reading them — no `NameError`
- Braces `{ }` create a scope (unlike Python's `if`/`else`) — a variable declared inside one
  doesn't exist after it

### STL containers
- `std::vector<int>`: `push_back`, indexing, `.size()`, range-based `for (int x : v)`, and RAII
  (frees its own heap memory on scope exit — no manual `delete`)
- `std::vector<bool>` initialized with size and default value (`std::vector<bool> primes(n+1, false)`)
- `std::array<int, 64>`: fixed-size, stack-allocated, size in the type, `.size()` returns `size_t`
  (unsigned) — mixing it with a signed loop counter is a known gotcha
- `std::unordered_map<K, V>` **is** Python's dict (hash table, O(1) average, no order).
  `std::map` is the other one — balanced tree, O(log n), keys sorted, no Python equivalent.
  The confusingly-named *unordered* one is the default choice
- `operator[]` inserts a default when reading a missing key — the reason an existence check must
  use `.find(key)` / `.end()`
- **Iterators and `->`**: `.find()` returns a *position*, not a value; `.end()` is a sentinel meaning
  "one past the last" and is **undefined behavior to dereference**. `it->second` is `(*it).second`.
  Rule of thumb: `.` on an object or reference, `->` on a pointer or iterator
- `std::pair<A, B>` — a generic two-field struct with members literally named `first`/`second`.
  Map elements are `pair<const Key, Value>`. Use a real `struct` when the fields have meaning
- C++17 **structured bindings** (`for (auto& [k, v] : m)`) — understood, not yet written in code
- `auto` type deduction and `&` reference-binding in range-based `for` to avoid copies
- `std::max` / `std::min` from `<algorithm>` — they return a *value* and discard which argument won

### Types, structs, classes
- `struct` definitions live at file scope so they're usable across functions; brace-init (`{0, 0}`)
  vs the comma operator (`(0, 0)`, wrong); `std::array` has no `<<` overload
- `struct` can group unrelated field types (e.g. `Screen{float WIDTH, float HIGHT, const char* TITLE}`);
  members accessed with `.`
- Classes: `class` with explicit `private:` / `public:` (vs `struct`, public by default); private
  data with public accessors; member functions can call each other unqualified
- **Const member functions**: a trailing `const` (`uint16_t getX() const`) is a compiler-enforced
  promise not to modify `*this`, and is *required* to call the method through a `const` reference
- `enum` for named constants, e.g. `enum State{X, EMPTY, O}`
- `static` has three unrelated meanings by position: in a function = initialized once, persists
  across calls; in a class = one shared copy (a Python class attribute); at file scope = internal
  linkage. `static constexpr` in a function is the idiom for a build-once lookup table
- `constexpr` — computed at compile time, implies `const`, everything in the initializer must be
  compile-time knowable. Storage class first: `static constexpr`
- C-style 2D arrays as function parameters, e.g. `uint64_t zobrist[4][3]`

### Strings & chars
- `char` (single character) vs `const char*` (pointer to a null-terminated array) vs `std::string`
  (RAII-managed string class); string literals are read-only, so `const char*` not `char*`
- **`+` on a `const char*` is pointer arithmetic, not concatenation.** `c + "Has Won!"` compiles
  and is a bug: the `char` promotes to `int` and the pointer advances that many bytes. For `+` to
  mean concatenation, **one operand must already be a `std::string` when the `+` is evaluated** —
  and the type you assign into does *not* reach back and change the parse. Convert inside the
  expression: `std::string(1, c)` uses the `(count, char)` constructor
- `.c_str()` — hands a `std::string`'s buffer to an API wanting a `const char*`

### Operators & numeric gotchas
- Bitwise: `&` tests, `|` sets, `& ~mask` clears, `^` toggles; `|=`/`&=`/`^=` compound assignment
- `&`/`|` bind **looser** than `==`/`!=` — `board & mask != 0` parses as `board & (mask != 0)`.
  Always parenthesize bitwise ops next to comparisons
- **Chained comparison doesn't exist.** `0 < x < 9` means `(0 < x) < 9` and is *always true* —
  a Python habit that compiles into a silently useless check. Write `0 <= x && x < 9`
- Float → `int` truncates **toward zero**, not floor — negative values collapse to 0 rather than
  going negative, so range checks still have to be explicit
- **NaN as a poison default**: `std::numeric_limits<double>::quiet_NaN()` (`<limits>`) is a value
  you can never legitimately *mean*, and it propagates through every arithmetic op, so a missing
  operand survives all the way to the output as `nan` instead of masquerading as a valid `0`.
  Choose a default the code can't confuse with real data
- **Every comparison against NaN is false** — `NaN < 0`, `NaN >= 10`, even `NaN == NaN`. A range
  check written as `if (x < lo || x >= hi) throw` therefore **lets NaN straight through**; the
  negated form `if (!(x >= lo && x < hi)) throw` catches it. Same IEEE semantics as Python, but
  here the bad index is undefined behavior rather than an exception
- Shifting by ≥ 64 or by a negative amount is **undefined behavior**, not a wrap or a zero —
  unlike Python, where `1 << 60000` just makes a big int. Validate indices before a shift
- Ternary `?:` — `(cond) ? a : b`, Python's `a if cond else b` with the operands reordered
- Use `true`/`false` (not `1`/`0`) for `bool`
- `#include <cmath>` and `sqrt()`
- Functions taking a parameter by value work on a copy — the caller must capture the return value

### Control flow
- `switch` takes integral/enum types only — no strings, no equivalent of Python's `match` on
  arbitrary objects. **Cases fall through**: a `case` without `break` runs the next case's body
  too, silently, and `/W4` does not warn. A `case` label doesn't open a scope either, so declaring
  a variable directly under one is a compile error (C2360) unless the body is wrapped in braces
- A range-based `for` cannot express a loop whose index moves non-linearly — it walks front to back
  and never revisits. Jumping requires a `while` over an index you control yourself

### Bitboards, hashing, search
- Bitboards: a `uint64_t` (or `uint16_t` for a small board) where each bit is one square;
  `1ULL << n` builds a mask (`ULL` needed — `1 << 63` on an `int` is UB); printing high-bit-first
  (63 → 0) matches place-value reading order; `std::bitset<N>` prints a fixed-width binary view
- Hashing (general): collapsing something complex into one small number used as a fast lookup key
- **Zobrist hashing**: one random key per (square) — or per (square, state)/(piece, colour, square);
  XOR them together for a position hash. XOR self-cancels (`A ^ B ^ B = A`), so "XOR out old, XOR
  in new" updates a hash incrementally; XOR is commutative/associative
- **Transposition table pattern**: probe on entry (`.find(key)` → return cached), store on exit
  (`tt[key] = best`), key grabbed **once** at the top so probe and store are provably the same slot.
  Probe *after* the cheap terminal checks. Never probe mid-loop and return early
- **Make/unmake, not copy-per-node**: mutate one board and restore it. The pair must be symmetric
  on *every* object the search touches — board and hash drifting apart is silent and produces
  confidently wrong moves. A guard on one object and not another is how desync starts
- Minimax scoring conventions: **fixed perspective** (scores from one side's view) pairs with a
  `maximizing` flag and `max`/`min`; **negamax** scores relative to the side to move and negates the
  child's return, needing no flag. Mixing them is incoherent. Initialize `best` **outside** the real
  score range (`±10`, not `0`) and per-branch
- Sentinel return values (`-1` for "no move") are the C++ substitute for Python's `None` when an
  `int`-returning function has a no-answer case — only useful if the caller checks

### Measurement & timing
- `std::chrono`: time points (`high_resolution_clock::now()`) and durations are distinct types;
  `duration_cast<microseconds>(...)` converts units, `.count()` pulls out the printable number.
  Compilers can delete a loop whose result is never used — keep a real data dependency
- **Count work, don't time it.** For anything finishing in milliseconds, run-to-run noise is larger
  than the effect. A counter threaded through as `int&` is exact and deterministic. Reset it
  immediately before the measured call and print immediately after. Compare against a **prediction
  made before running** — that's what turns a number into evidence

### Randomness
- `std::mt19937_64`: a random *engine* object (seed once, call `rng()` repeatedly) — not a plain
  function like Python's `random.randint`; seedable with a fixed int (reproducible) or
  `std::random_device` (non-deterministic)
- `std::uniform_int_distribution<uint64_t>` paired with an engine for full-range values

### Exceptions
- `try { } catch (const std::out_of_range& e) { }` — Python's `try`/`except` with braces.
  `catch (...)` is bare `except:`; `throw X("msg");` is `raise`; `e.what()` is `str(e)`
- **Catch by `const&`, always.** By-value catch copies and *slices* off the derived part of the
  exception. `/W4` does not warn
- **There is no `finally`.** Stack unwinding runs the destructor of every local object on the way
  out, so `vector`/`string` free themselves — but raw `new` leaks. The destructor *is* the cleanup
  guarantee; this is the strongest argument for RAII
- **`exit()` bypasses all of it.** `std::exit(EXIT_FAILURE)` (`<cstdlib>`) terminates *without*
  unwinding the stack, so destructors of local objects never run — the one construct that voids the
  RAII cleanup guarantee. It also walks around every `catch` in the call chain. Inside a
  library-shaped function (a VM, a parser, a tokenizer) it's almost always wrong: that frame doesn't
  know whether it's driving a REPL, a test, or a pipeline — the caller does. Throw and let `main` decide
- **Detect–report–continue is worse than crashing.** Printing an error and carrying on leaves the
  program running on state that no longer means anything, and it produces a confident wrong answer
  with a success exit code. Four appearances now (the tokenizer's `Failure` token ×3, the VM's
  failed `LOAD`). Pick one: throw, or don't detect it at all
- **One class of failure, one mechanism.** If `pop()` throws on underflow, then "the bytecode asked
  for data that isn't there" throws *everywhere* — a second mechanism for the same category means
  the caller has to handle both, and usually can't handle one of them
- **Code after a throwing call is not cleanup.** Anything in the `try` below the throw is skipped.
  Reset persistent state **on entry**, not on the way out — every `return` added later is a new way
  to skip an exit-cleanup
- Uncaught → `std::terminate`: no traceback, no message, just a hex exit code (MSVC: `0xC0000409`)
- Hierarchy: `std::exception` → `logic_error` → `invalid_argument` / `out_of_range`; also
  `runtime_error`. Catches are tried **first-match, not best-match** — most-derived first
- `std::stoi` throws `invalid_argument` (nothing convertible) or `out_of_range` (doesn't fit
  `int`; `INT_MAX` is 2147483647). **It ignores trailing garbage** — `stoi("42abc")` returns 42
  silently, unlike Python's `int()`. Will matter for decimals
- MSVC needs `/EHsc` to enable exceptions (already in the build task); `#include <stdexcept>`
  explicitly — MSVC's `<string>` pulls it in transitively, libc++ on the Mac may not
- `std::cout << e` is a **compile error** — no `operator<<` for exceptions. Unlike Python, printing
  a type with no overload doesn't fall back to anything. Use `e.what()`
- Overload-resolution errors dump every candidate as `note:` lines. **Read the first line, ignore
  the notes** — the opposite of reading a Python traceback bottom-up

### Class mechanics
- `= default` is a **declaration**, so it obeys the `public:`/`private:` section it sits in — a
  private default constructor makes the class un-instantiable (C2248). Also: you only need it when
  you've declared *another* constructor; otherwise it's noise
- **Default arguments** (any function, not just constructors): `= value` after the parameter, same
  idea as Python's `def f(x, times=1)`. Three differences: it goes on the **declaration** (when a
  class is later split into a header and a `.cpp`, repeating it on the definition is C2572);
  everything after the first defaulted parameter must also be defaulted, because C++ has no
  keyword arguments and fills them left to right; and the expression is evaluated **at the call
  site on every call**, so there's no function object to hold state and no Python mutable-default trap
- In-class member initializers (`Type type{Failure};`) are the fix for uninitialized members.
  Defaulting to the *error* state rather than a valid one makes a half-built object detectable
- Uninitialized members produce silent wrong behaviour, not a crash: an uninitialized index made
  the first call return zero tokens while every later call worked
- **Most vexing parse**: `VM vm();` declares a *function* taking no arguments and returning `VM`,
  not an object — the next line's `vm.run(...)` then fails to compile. Write `VM vm;` or `VM vm{}`.
  Pure C++ grammar ambiguity, no Python analogue

### Streams & input
- `while (std::getline(std::cin, line))` — the stream converts to `bool`, so the read *is* the loop
  condition. One call, not a test-read plus a real read. Without it, EOF stops blocking and the
  loop spins forever
- Print the prompt at the **bottom** of the loop body (or before it, not both) or it appears one
  line ahead of the output it belongs to. A `continue` that skips it is the same bug wearing a
  different hat — the prompt has to print on *every* path
- **`std::cout` defaults to 6 significant digits for floating-point.** `1234567` prints as
  `1.23457e+06` — not just ugly, *wrong*. `std::setprecision(15)` (`<iomanip>`) is about the useful
  limit for a `double` and leaves `7` as `7` and `3.5` as `3.5`. Avoid `std::fixed` unless you want
  `7.000000`
- Stream manipulators are **sticky** — `setprecision`, `hex`, `setfill` change the stream's state
  permanently, not just the next insertion. Set once; a stray one anywhere silently changes output
  much later

### Multi-file projects
- Multi-file Python projects (`from module import ...`) — the concept transfers; the C++
  mechanism (headers, translation units, linking) is still new

### CMake
- CMake is a **generator**, not a compiler: `cmake -S . -B build` (configure) writes the platform's
  real build system; `cmake --build build --config Debug` runs it
- Everything hangs off a **target** made by `add_executable(name srcs...)`. `target_*` commands
  must come after it and must use that exact name — **case-sensitive, and not the `project()`
  name**. Mismatch → "Cannot specify compile features for target ... not built by this project"
- `PRIVATE` = applies to this target only; the answer for an executable
- Per-compiler flags behind `if (MSVC) ... else() ... endif()`. Flags in the wrong branch fail
  silently: `cl` ignores `-Wextra` (D9002) and reads `-Wall` as `/Wall`; an empty `else()` gives
  the Mac zero warnings
- A typo'd `--build` drops cmake back into configure mode, so the errors describe the *rest* of
  the line ("Unknown argument --config"), not the typo
- **Incremental builds only warn on files they recompile.** An unchanged file is skipped, so its
  warnings don't reappear. `--clean-first` forces a full recompile when the warning count matters
